GRUPO 1 Compre Rápido • Resolução de Crise Black Friday
O Problema Diagnóstico Nova Arquitetura Tecnologias

Relatório de Eng. de Arquitetura & DevOps

Análise de Gargalo, Diagnóstico Monolítico e Proposta de Escalabilidade Horizontal para o E-commerce Compre Rápido.

CENÁRIO DE CRISE DETECTADO: Servidor monolítico fora do ar por saturação de CPU durante o pico da Black Friday.

1. O Problema: A Falha na Black Friday

A plataforma Compre Rápido operava sob uma arquitetura monolítica tradicional hospedada em um único servidor. Com o aumento repentino do tráfego na Black Friday, a CPU do servidor atingiu 100% de utilização, resultando em indisponibilidade total do sistema e perda de vendas.

Sintomas Observados

  • Timeouts em requisições HTTP (Status 504 Gateway Timeout).
  • Saturação severa de CPU e memória RAM no servidor central.
  • Incapacidade de processar pagamentos e checkout simultâneos.

Causa Raiz

  • Acoplamento excessivo de serviços (Catálogo, Carrinho, Autenticação e Pagamento na mesma máquina).
  • Dependência de Escala Vertical (Scale-Up), que possui limites físicos e alto custo financeiro.
  • Ponto único de falha (SPOF - Single Point of Failure).

2. Diagnóstico Técnico: Monolito vs. Escala Vertical

A escala vertical consiste em adicionar mais hardware (CPU/RAM) à mesma máquina. Essa abordagem falhou pelos seguintes motivos:

Métrica / Conceito Escala Vertical (Monolito) Escala Horizontal (Proposta)
Resiliência Baixa (Se o servidor cai, tudo cai) Alta (Réplicas mantêm o sistema no ar)
Limite Financeiro/Técnico Possui teto (Hardware de ponta é caríssimo) Flexível (Adiciona instâncias simples conforme a demanda)
Manutenção & Deploy Risco alto (Deploy afeta o sistema todo) Independente (Microsserviços / Containers)

3. Arquitetura Recomendada & Estratégias

Para garantir tolerância a falhas e alta disponibilidade para os próximos eventos de alto tráfego, projetamos uma arquitetura baseada nos seguintes pilares:

🚀

Escalabilidade Horizontal (Scale-Out)

Distribuição do tráfego entre múltiplos nós/containers rodando instâncias da aplicação. Uso de Load Balancer (Nginx/HAProxy) para divisão de carga.

🗄️

Sharding de Banco de Dados

Particionamento horizontal dos dados (ex: por ID de cliente ou região) em diferentes nós de banco de dados, aliviando gargalos de I/O de leitura e escrita.

🛡️

Tolerância a Falhas Automática

Implementação de Health Checks constantes e Auto-Scaling. Se uma instância falhar, o Load Balancer redireciona a requisição e um novo container é subido automaticamente.

4. Implementação DevOps & Publicação em Nuvem

A interface do projeto foi conteinerizada para garantir consistência de ambiente do desenvolvimento à produção no Render.

Dockerfile (Produção com Nginx)
# Imagem base leve do Nginx
FROM nginx:alpine

# Copia os arquivos da aplicação para o diretório do Nginx
COPY . /usr/share/nginx/html

# Expõe a porta 80
EXPOSE 80

# Inicia o servidor Nginx
CMD ["nginx", "-g", "daemon off;"]
